# Видалення даних і зв'язки

Міграція `0003_data_lifecycle.sql` переводить car_documents/car_shares/station_reviews під контроль міграцій, додає індекси та перевірки батьків у SQL. Runtime CREATE TABLE більше немає. Міграція адитивна й повторно виконувана; вона не виправляє старі orphan-рядки автоматичним видаленням.

Звичайне видалення автомобіля блокується, поки є пов'язані записи або чеки. Потрібно спочатку видалити їх. Після видалення авто QR-каталоги видаляються; видалення чека відкликає snapshot, у якому чек був дозволений. Вже завантажену копію документа відкликати неможливо.

У профілі є окрема дія видалення всіх даних із фразою `ВИДАЛИТИ МОЇ ДАНІ`. DELETE `/api/account-data` вимагає входу, правильного Origin, JSON до 500 байтів і точної фрази без зайвих полів. GET повертає стан лише власника. Жоден GET нічого не видаляє.

Перед очищенням SQL створюється бар'єр запису. Тригери не дають запізнілим запитам додати записи, документи, фото, відгуки або QR-каталоги. Видаляються всі owner-scoped records, документи, зв'язки, спільні каталоги, фото/пошукові завдання та відгуки; персональні ліміти пошуку та звичайні API-лічильники очищаються. Короткочасний хешований ліміт самого видалення зберігається до expiry, щоб повторна дія не скидала захист. Глобальні відкриті VIN/МВС-кеші не є приватними записами профілю й не змінюються цією операцією.

Файлові ключі спочатку копіюються в чергу. За одну дію видаляється до 25 файлів; R2-помилки залишають чергу для повтору. HTTP 202 означає незавершене файлове очищення, HTTP 200 — відсутність черги й файлів під owner-prefix під час перевірки. Повторити дію безпечно. Після підтвердження браузер сам продовжує порції 202, враховує Retry-After для 429 і зупиняється після повторних збоїв сховища; після перезавантаження показує можливість продовжити. Закриття вкладки зупиняє клієнтський цикл, але не відновлює видалені записи. Фоновий гарантований завершувач черги не налаштований. Нові фото й чеки використовують owner-prefix; старі фото з ключами vehiclephotos беруться з наявних метаданих. Раніше втрачені orphan-файли без метаданих/owner-prefix потребують окремого storage-аудиту. Незавершений старий upload при аварійному завершенні процесу також потребує повторного очищення.

**Що зберігається:** мінімальна відмітка platform subject ID, стан і технічний час видалення. Без VIN, імені, історії та вмісту файлів. Вона потрібна для write barrier й наразі постійна: цей профіль не зможе створювати нові дані Motorna. Це явно написано перед підтвердженням. Видалення не видаляє обліковий запис ChatGPT, журнали платформи, зовнішні оголошення або сторонні резервні копії. Політику їхнього зберігання треба затвердити окремо.

`tests/data-lifecycle.mjs` перевіряє справжній SQL міграцій у SQLite: повторне застосування, RESTRICT для чека, QR revocation, перевірки батьків, 33 файли, R2-помилку/повтор, незмінність іншого власника, бар'єр запізнілого запису, auth/CSRF/body limit. Це не remote D1/R2 restore rehearsal. Реальні дані власника в тесті не використовуються.
