# Підготовка money-v2

Статус: підготовлено, не активовано. Production і локальні користувацькі дані не мігровані. Поточні API/інтерфейс ще використовують major units; застосовувати підготовлений пакет до робочої бази до оновлення читачів/записувачів не можна. Міграції немає в автоматичній папці drizzle/.

## Формат

```json
{"moneyVersion":2,"amountMinor":12345,"currency":"UAH"}
```

12345 — 123,45 грн. Підтримано UAH/EUR/USD/GBP із scale=2. Інші валюти блокуються, їх scale не вгадується. app/money.ts містить точне decimal → integer перетворення й додавання лише однакових валют із перевіркою Number.isSafeInteger. Множення float на 100 та неявного округлення немає. Значення з більш ніж двома десятковими знаками, у тому числі неоднозначні артефакти float, потребують ручного рішення.

| Джерело | Старі поля | money-v2 |
|---|---|---|
| records: expense, plan | amount | amountMinor + currency |
| records: cart | price, delivery | priceMinor, deliveryMinor + спільна currency |
| records: purchaseRequest.lines[] | price, currency | priceMinor, currency |
| records: searchHistory.results[] | price, currency | priceMinor, currency |
| records: webFavorite | price, currency | priceMinor, currency |
| car_shares.payload.history[] | amount | amountMinor + currency |

moneyVersion=2 встановлюється в корені payload. Старі грошові поля видаляються лише з перетвореного payload. Негрошові поля, власник, ідентифікатори, created, документи та зв’язки не змінюються. Запити без ціни залишаються без ціни — не нуль. Змішані major/minor поля, невідома версія, валюта або небезпечне число блокують підготовку. Уже коректний v2 перевіряється і пропускається.

Для expense/plan/cart і QR-історії пропущена валюта заповнюється тільки явно обраним оператором legacyCurrency. Перед вибором UAH потрібно підтвердити, що саме в гривнях були ці історичні суми. У цін магазинів currency має бути в самому джерелі; --legacy-currency їх не доповнює й не змінює наявну валюту.

## Dry-run на копії

Потрібен Node.js 24 та узгоджений офлайн-знімок SQLite з records і, якщо є, car_shares. Активний WAL-файл без належної копії не є узгодженим знімком. Експорт D1 у SQL спочатку відновлюється в окрему SQLite-копію, не поверх робочої бази.

```sh
node scripts/prepare-money-migration.mjs --database .money-migration/snapshot.sqlite --out-dir .money-migration/review-01 --legacy-currency UAH
```

Скрипт відкриває джерело readOnly, читає обидві таблиці в одному snapshot та нічого не застосовує. Каталог результату має бути новим. Усередині репозиторію дозволено лише .money-migration/, який ігнорується Git; зовнішній приватний каталог також дозволено. Snapshot, report і rollback містять приватні дані: їх не публікують, не додають до Git чи запитів підтримки. Права файлів обмежуються, наскільки це підтримує ОС; на Windows потрібні належні ACL каталогу.

Результат без проблем:

- report.json — підсумки та політика legacy currency.
- apply.sql / rollback.sql — транзакційні скрипти для офлайн SQLite.
- d1-apply.json / d1-rollback.json — масиви параметризованих SQL-операцій для одного контрольованого D1 batch.

Якщо є неоднозначні рядки: exit code 2, лише report.json; виконувані пакети не видаються. Звіт показує до 1000 ключів проблемних рядків і загальний issueCount. Рядки перевіряють приватно; суми й payload не друкуються у stdout. Після виправлення копії готується новий каталог. Exit code 0 означає «пакет підготовлений», не «міграція застосована».

## Захист застосування та відкат

Оновлення має умову точного збігу ключа, власника, kind (для records) і старого payload. Перед кожним UPDATE перевірка CHECK примусово зупиняє пакет, якщо рядок змінився/зник. Для офлайн SQLite INSERT OR ROLLBACK повертає назад також попередні UPDATE. Відкат перевіряє очікуваний v2 payload та відновлює оригінальний JSON, а не повторно обчислений float. Нові зміни користувача не перезаписуються: при конфлікті потрібен новий план або окреме рішення.

Для D1 не використовуйте SQLite apply.sql з BEGIN/COMMIT. Підготовлений JSON передається в db.batch як db.prepare(op.sql).bind(...op.params). Пакет містить унікальну guard-таблицю з CHECK, перевірки, UPDATE та DROP guard-таблиці; явних BEGIN/COMMIT немає. Властивість відкату batch описана в [офіційній документації D1](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). Перед staging потрібно перевірити актуальні ліміти розміру/кількості запитів і вміст пакета. Не розбивайте його довільно: кілька batch вже не є однією атомарною міграцією. Для великих баз потрібна окрема стратегія поетапного переходу з журналом.

## Порядок активації

1. Перевірити backup/restore на staging; підготувати dry-run і виправити всі issues.
2. Додати читання v1/v2 у API, parseRecord, QR-каталог, CSV/Excel/PDF і TXT. Перенести підсумки та quantity × price на перевірені цілі числа; не змішувати валюти.
3. Оновити схеми POST/PATCH, UI та імпорт цін на v2. Перевірити повторні запити Idempotency-Key зі старими знімками й форматами; старі клієнти не повинні повторно записувати major units.
4. Зупинити старі записувачі на час контрольованої міграції, отримати свіжий знімок, перевірити staging apply/rollback і підсумки окремо за валютою.
5. Лише потім погоджений production-перехід із відповідною версією застосунку. До цього пакети залишаються підготовчими; поточна публікація їх не виконує.

## Перевірка

`node tests/money-migration.mjs` входить у npm test: 6 типів записів, QR, точні дроби, валюти, пропущені ціни, неоднозначності, read-only CLI, конфлікт після попереднього UPDATE, точний rollback та повторний dry-run без повторного множення. SQL і параметризований пакет перевірено на SQLite.

Окремий `node --import ./scripts/sites-env.mjs tests/money-d1.mjs` призначено для нативної staging-репетиції D1 через Miniflare. У поточному Windows-середовищі Workers runtime двічі завершився ERR_RUNTIME_FAILURE / access violation до запуску SQL. Тому нативну D1-перевірку не позначено успішною; вона потрібна перед активацією. Тест не входить у стандартні офлайн-регресії та не підключається до production.
