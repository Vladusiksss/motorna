# План закриття відкритих пунктів релізу

Знімок стану: 11.11.2026. Статус «частково» означає, що кодова основа існує, але production-доказу або повного завершення немає. Контрольовані локальні перевірки не прирівнюються до зовнішнього аудиту, ліцензійного доступу чи staging-репетиції.

## 1. Обов'язкові передумови релізу

| № | Робота | Стан і наступний крок |
|---|---|---|
| 1 | Резервна копія D1/R2 і повне відновлення | Відкрито. Потрібні операторський доступ до production export, окремі staging D1/R2 і зашифроване сховище backup. Зробити snapshot, відновити staging, звірити кількість рядків/зв'язків/об'єктів/контрольних сум, пройти відкликання QR, зберегти журнал доказів. До цього backup не вважати перевіреним. |
| 2 | Антивірус і PDF sanitization | Відкрито. Потрібні вибір і доступ до scanner API або контрольованого сервісу ClamAV та підтримуваний PDF sanitizer у runtime. Підключити fail-closed сканування до збереження в R2, карантин/відмову інфікованих файлів, санітизацію активного вмісту й безпечний повторний download. |
| 3 | Незалежний security audit | Відкрито. Потрібен незалежний аудитор і погоджений scope/доступ до staging. Scope: авторизація, сесії, API, upload, abuse/rate limits, видалення. Публікувати лише узгоджений звіт і remediation-tracker. |
| 4 | Повне видалення акаунта та файлів | Контрольований цикл підтверджено: повний `npm test` пройшов data lifecycle, orphan/owner-isolation, помилки й повтори R2, tombstone/write barrier та SQL races. Віддалена перевірка orphan-файлів і залишкових записів не виконана. Після надання staging/R2 доступу пройти реальний профільний цикл і звірити всі таблиці, R2 prefix та legacy object keys. |
| 5 | Юридичне затвердження | Відкрито. Потрібні підтверджені реквізити оператора, контакт для звернень, юрисдикція та погоджені строки зберігання. Юрист/оператор затверджує політику; дані не вигадувати. |

## 2. Архітектура

| № | Робота | Стан і наступний крок |
|---|---|---|
| 6 | Єдині DTO API | Частково зроблено й локально перевірено: спільні схеми запитів у `app/modules/shared/contracts.ts`, типізовані контракти у `app/api-contracts.ts`, спільний error envelope у `app/api-response.ts`; API-contract regression проходить. Наступне: інвентаризувати кожен handler, перевести винятки на спільні DTO і зафіксувати OpenAPI/контрактну таблицю. |
| 7 | Money v2 | Частково: `app/money.ts` і DTO підтримують ціле `amountMinor` та валюту; migration/rollback fixtures пройшли у regression suite, але старі API, записи, UI та експорт ще використовують decimal `amount`. Після пункту 1 завершити dual-read/backfill у staging, перевести всі клієнти й експорт, звірити суми та лише потім активувати міграцію. |
| 8 | Фонові задачі | Частково: regression suite підтверджує D1 lease/cache/retry-races; є атомарний lease для каталогу та повторний запуск за запитом. `waitUntil` не є довговічною чергою. Потрібен scheduler/queue binding для автоматичного відновлення, lease-expiry моніторинг і алерт завислих задач. |
| 9 | Моніторинг | Частково: health/privacy probes і workflow описані в `MONITORING.md`; Telegram вимкнено, доставка не підтверджена. Потрібні GitHub secrets, числовий chat ID і явне ввімкнення власником, потім контрольна доставка та зовнішні API probes. |
| 10 | Розподілений rate limiting | Контрольовані concurrency/atomicity, власник/scope/window, TTL cleanup, 429/Retry-After та fail-closed перевірки пройшли у regression suite. Відкрито production навантажувальне підтвердження на різних Worker instances і перевірка меж D1/WAF. |
| 11 | Логи, кореляція та latency | Частково: кожна відповідь API тепер має структурований JSON completion log з `requestId`, route, method, status та `durationMs`, без query/body. Потрібні централізоване зберігання, latency percentiles і алерти у вибраному провайдері. |
| 12 | ESLint warnings | Виконано: усі 65 попереджень усунуто; `eslint . --max-warnings=0` проходить без попереджень та помилок на Node 24. Strict-поріг увімкнено в `package.json`. |

## Порядок виконання

1. Надати окремі staging D1/R2 та захищене місце для backup; виконати пункти 1 і 4.
2. Вибрати scanner/PDF sanitizer та провайдера моніторингу; завершити пункти 2, 9 і 11.
3. Замовити незалежний аудит і затвердити юридичні реквізити/строки (3 і 5).
4. Завершити Money v2 після staging backup (7), перевірити фонове відновлення та rate limits (8 і 10).
5. Отримати договори/ключі партнерів для пунктів 13–20; інтегрувати кожне джерело окремим адаптером і перевірити реальні позитивні результати.
6. Закрити інтерфейсні пункти 21–25 і зняти production-метрики.

11.11.2026: `npm test` — усі 32 regression suites пройшли; `tsc --noEmit` пройшов; `npm run lint:strict` пройшов із 0 попереджень; production build пройшов, але повідомив про client chunk понад 500 kB. Production smoke пройшов усі read-only перевірки. E2E показав `ok` для кожного з 28 desktop/mobile сценаріїв, але runner не завершився після останнього сценарію і був зупинений, тому повний запуск позначено непідтвердженим.

Кожен зовнішній етап закривається лише артефактом доказу: staging-звіт, scan test report, незалежний audit report, юридичне погодження, delivery receipt або production-метрики. Локальний код чи mock самі по собі не є таким доказом.
