# Перевірки MOTORNA

## Швидкі перевірки
- `npm run typecheck` — TypeScript без генерації файлів.
- `npm run lint` — повна перевірка ESLint без baseline; 0 помилок.
- `npm run lint:strict` — та сама повна перевірка; проходить. Попередження не приховано.
- `npm test` — 21 регресійний наборів без зовнішніх джерел.
- `npm run build` — production build.

## API
Запустіть локальний dev-сервер і `npm run test:api`. Перевіряються збережений VIN, діагностика, приватний запит, повторне читання, TXT, відмова анонімному користувачу, чужому carId та demo-товарам. Видаляються тільки записи цього тесту. Запуск проти віддаленого домену заборонений у тесті.

## Playwright E2E
Після `npm ci` встановіть Chromium: `npx playwright install chromium`. Запуск: `npm run test:e2e`. Сервер запускається й завершується засобами Playwright; локальний уже запущений сервер можна повторно використати. В CI повторне використання вимкнено. Використовується тільки localhost і локальна тестова ідентичність Sites. Production-ключі та облікові записи не потрібні.

Чотири сценарії для desktop 1440×1000 і mobile 375×812:
1. VIN → підтвердження авто → артикул → фільтр виробника → непідтверджена сумісність → кількість → приватний запит → reload → TXT. Demo-пропозиція не додається. Перша відповідь збереження навмисно губиться: повтор має той самий ключ і створює лише одну чернетку.
2. HTTP 503 від джерела → відсутність вигаданих товарів/цін → запит на підбір без ціни.
3. Перемикання авто в гаражі → попереднє QR-посилання та зображення не переносяться до іншого авто.
4. Початковий екран приховує невідомі характеристики; режими VIN / Запчастина / Симптоми змінюють поле пошуку.

Зовнішні відповіді VIN, фотографій та магазинів у браузерних тестах — контрольовані фікстури. Третій сценарій додатково підміняє відповідь QR-API лише для перевірки ізоляції стану. Тести не підтверджують доступність продавця, справжню ціну або OEM-сумісність. Авторизація, записи, валідація власника та TXT працюють через справжній локальний сервер і базу. Тестові записи очищаються за власними VIN; чужі записи не видаляються. У робочому застосунку немає умовних E2E-обходів прав доступу.

`playwright-report/` містить HTML-звіт; `test-results/` — скріншоти успіху та traces помилок. Вони ігноруються Git. Actions завантажує звіт з обмеженим строком зберігання 7 днів. Запуски не публікують сайт. Для production потрібна окрема перевірка зовнішніх API без заміни відповідей.

Конфігурація: `playwright.config.ts`, `tests/e2e/purchase.spec.ts`, `.github/workflows/ci.yml`. Тайм-аути враховують холодну компіляцію dev-сервера; фіксованих sleep у браузерних тестах немає.

## Перевірки доступу та документів
`tests/access-security.mjs` виконує реальні серверні функції маршрутів проти SQLite у пам’яті та тестового сховища файлів. Лише серверна ідентичність підмінена на A/B/анонімного користувача; production-авторизація та dev sign-in не змінені. Перевіряються списки/редагування/видалення чужих записів, чужі carId у витратах/запитах, приватні документи, включення лише дозволених чеків у QR, відкликання збереженого URL та cross-site заборона відкликання. Це не аудит зовнішнього провайдера авторизації або проникнення у production.

`tests/document-upload.mjs` перевіряє сигнатури, порожні файли та потік понад ліміт із неправдивим Content-Length. `tests/health.mjs` перевіряє DB/R2 probe, TTL, 503 і відсутність внутрішніх повідомлень помилок у відповіді. Існуючий `tests/car-catalog.mjs` додатково перевіряє відкликання документа за старим URL.

## Production smoke
`npm run test:production` виконує лише читання сторінок/health і діагностичний запит із загальним тестовим текстом. Перевіряє 401 для анонімного читання записів і документів. Записи, файли й QR не створюються. Успіх характеризує момент запуску, не історію uptime. Не запускається в офлайн-регресіях; зовнішній збій справді призводить до помилки.

Ідемпотентність у `access-security.mjs`: п’ять одночасних POST із тим самим ключем, повтор після втрати відповіді, інший вміст із тим самим ключем (409), невалідний ключ (400), ізоляція ключів між A/B. SQLite має той самий primary key, що й D1.

Додаткові 4 браузерні перевірки (desktop/mobile): відновлення підтвердженого VIN після входу та глобальні команди артикула/симптомів для вибраного авто. Разом 12 тестів. `api-contracts.mjs` перевіряє некоректні зовнішні структури, межі рейтингу, вкладений JSON-LD та помилки API.

`record-integrity.mjs` детерміновано призупиняє кожний POST/DELETE перед SQL-записом і запускає конкурентну дію. Перевіряє обидва порядки для expense/searchHistory/purchaseRequest (з ключем повтору й без), 409 при пов’язаних записах, 404 після видалення авто, видалення дочірнього запису та ізоляцію власників. Окремий anti-join перевіряє, що сирітських записів немає. Міграція не потрібна: умови цілісності входять у самі INSERT/DELETE.

Пагінація: `records-pagination.mjs` перевіряє межу 1–100, порядок при однаковому created, обхід усіх сторінок без повторів, kind/carId/id/from/to, власника, невалідні/чужі курсори та EXPLAIN QUERY PLAN для чотирьох індексів без TEMP B-TREE. Міграція перевіряється на наявних рядках без втрати даних. `record-client.mjs` перевіряє повний експорт усіх сторінок, збереження фільтрів і відмову при збої або зацикленні курсора. Два додаткові E2E desktop/mobile створюють 61 витрату: видимі 50, CSV містить 61, кнопка завантажує решту; старіше авто залишається вибраним. Разом 16 браузерних тестів, включно з Origin/CSRF: справжні браузерні JSON та multipart-запити працюють; підроблені PATCH/DELETE не змінюють записи.


`json-body.mjs` перевіряє ліміт фактичних UTF-8 байтів, межу рівно в ліміт, однобайтові чанки, відсутній/неправдивий Content-Length, дострокове скасування, некоректні JSON/UTF-8, обрив та помилки потоку. Усі 12 JSON-обробників використовують спільне читання. Access security додатково перевіряє 413 для POST/PATCH записів і QR без зміни бази. Production smoke перевіряє 413 та 400 на API аналізу без збереження даних.
